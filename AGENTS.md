# Backend Project Instructions

## Technology

Build the backend as an ASP.NET Core Web API using:

- .NET `10`
- Entity Framework Core
- PostgreSQL with the `postgres:18-alpine` container image
- OpenAPI/Swagger documentation
- Asynchronous APIs with cancellation support

Keep backend implementation in this repository. Frontend implementation belongs to its separate project repository.

## Clean Architecture

Organize the solution into clear layers with dependencies pointing inward:

- `Domain`: entities, value objects, domain rules, and domain interfaces. This layer must not depend on infrastructure or ASP.NET Core.
- `Application`: use cases, commands/queries, DTOs, validators, application interfaces, and business workflows. Depend only on `Domain` and stable abstractions.
- `Infrastructure`: EF Core, database configuration, repositories, email provider integration, background processing, and other external services.
- `WebApi`: controllers or endpoints, middleware, dependency injection, configuration, authentication, OpenAPI, and HTTP concerns.

The `WebApi` layer composes the application and infrastructure layers. Do not place business rules in controllers, EF Core entities, or API-specific model binders. Do not expose domain entities directly as API responses.

## Functional Requirements

### Credit Registration

Provide an API operation to register a credit with:

- Client name
- Client ID or identification number
- Credit amount
- Interest rate
- Term in months
- Commercial representative derived from the authenticated user
- Registration date generated by the backend

The API must:

- Validate all fields server-side, including required values, ranges, and valid numeric formats.
- Use request and response DTOs.
- Derive the commercial representative from the authenticated user's identity or JWT claims; never trust a commercial value supplied by the client.
- Require authentication for credit registration and consultation endpoints.
- Persist the credit before scheduling email notification.
- Return appropriate HTTP status codes and a stable response shape.
- Avoid duplicate submissions where an idempotency strategy is applicable.

### Credit Consultation

Provide an API operation to retrieve registered credits, including:

- Client name
- Client ID
- Credit amount
- Interest rate
- Term in months
- Commercial representative
- Registration date

Filtering and sorting must be performed server-side. Support:

- Filtering by client name
- Filtering by client ID
- Filtering by commercial representative
- Sorting by registration date
- Sorting by credit amount

Use validated, explicitly supported query parameters. Never map arbitrary user-provided strings directly to SQL or entity properties. Prefer pagination with page size limits and total-count metadata so the API does not load an unbounded dataset.

## Asynchronous Email

After a credit is registered, send an email to `fyasocialcapital@gmail.com` containing:

- Client name
- Credit amount
- Commercial representative
- Registration date

Email delivery must be independent of the registration request. The registration endpoint must not wait for SMTP or email-provider delivery to complete.

- Hide email delivery behind an application interface.
- Implement a producer/consumer pattern: the registration use case produces a notification message, and a background consumer processes messages from a bounded queue or durable outbox.
- Use a hosted worker for queue consumption and keep queue operations asynchronous.
- Make the email operation retryable and idempotent.
- Record failures and retry exhaustion through structured logs and an observable status mechanism where practical.
- Prevent email credentials and provider configuration from entering source control.
- Do not allow email-provider failures to roll back a successfully persisted credit unless the business requirement explicitly changes.

## API and Error Handling

- Maintain OpenAPI documentation for all public endpoints, request models, response models, query parameters, and error responses.
- Use consistent HTTP status codes, including validation errors, conflicts, and unexpected failures.
- Return RFC 7807 `ProblemDetails` responses for errors.
- Add centralized exception handling middleware or the equivalent ASP.NET Core mechanism.
- Keep controllers/endpoints thin and delegate work to application use cases.
- Accept and propagate `CancellationToken` through the API, application, database, and external-service calls.
- Use structured logging with useful correlation information.
- Never return stack traces, secrets, connection strings, or internal implementation details in production responses.
- Configure CORS explicitly for the deployed frontend origins.
- Add health checks for the API and database readiness.

## EF Core and PostgreSQL

- Use EF Core migrations as the source of truth for schema changes.
- Include clear migration and database setup instructions in `README.md`.
- Use PostgreSQL-compatible types and configure constraints explicitly.
- Store credit amounts as integer monetary units without decimal fractions, using a PostgreSQL integer-compatible type such as `bigint`; never store formatted values such as `"300.000"`.
- Use precise decimal columns for interest rates and never use floating-point types for rates or monetary calculations.
- Store registration timestamps in UTC and expose a documented date format.
- Add indexes for fields used frequently in filtering and sorting when justified by query patterns.
- Use `AsNoTracking()` for read-only queries.
- Project queries directly to response DTOs to avoid over-fetching.
- Avoid N+1 queries and unintended lazy loading.
- Apply maximum page sizes and query limits.
- Keep EF Core configuration in infrastructure configuration classes where practical rather than coupling the domain to persistence details.
- Use transactions only around workflows that require atomicity and keep transaction boundaries in the application/infrastructure workflow.
- Use parameterized EF Core queries and avoid raw SQL unless it has a documented reason and remains parameterized.

## Validation and Security

- Treat every request as untrusted input.
- Validate at the API boundary and enforce business invariants in the domain/application layers.
- Use allowlists for sortable fields and filter operations.
- Never build SQL from raw request values.
- Keep secrets in environment variables, local secret storage, or a managed secret provider.
- Do not commit `.env` files, passwords, tokens, certificates, or private keys.
- Require authentication for registration and consultation so the backend can identify the commercial who registers each credit. JWT is the preferred approach unless an equivalent session-based design is deliberately chosen.
- Apply rate limiting to public or write-heavy endpoints where appropriate.
- Configure HTTPS and secure headers for deployed environments.

## Docker and Compose Guidance

When Docker support is added, create a `compose.yaml`, a multi-stage backend `Dockerfile`, and a `.dockerignore`.

The Compose setup must follow these practices:

- Use the pinned `postgres:18-alpine` image, never `latest`.
- Define separate API and PostgreSQL services.
- Use a named volume for PostgreSQL data persistence.
- Add a PostgreSQL health check using `pg_isready`.
- Make the API depend on PostgreSQL health, not merely container startup.
- Use the Compose service name as the database hostname inside the network; never use `localhost` for container-to-container access.
- Keep PostgreSQL on the internal Compose network and expose its port to the host only when local development requires it.
- Expose only the API port required by the frontend or local development.
- Configure connection strings, credentials, ports, and email settings through environment variables.
- Use an untracked `.env` file for local values and provide a safe `.env.example` without secrets.
- Do not put credentials directly in committed Compose files.
- Use a restart policy appropriate to the environment.
- Do not use the obsolete Compose `version` field.
- Use explicit service health checks and graceful shutdown behavior.
- Run migrations as a deliberate deployment/setup step rather than blindly on every container restart.
- Keep development conveniences separate from production deployment settings.
- Configure the final API image to run as a non-root user where supported.
- Use a multi-stage build so the final image contains runtime artifacts only.

The `.dockerignore` must exclude at least `.git`, `.env` files, `bin`, `obj`, test results, IDE metadata, logs, local certificates, private keys, and other build artifacts.

## Testing and Quality

Add automated tests for:

- Domain rules and invariants
- Request validation
- Authentication and authenticated commercial identity derivation
- Credit registration use case
- Integer monetary value persistence and serialization
- Server-side filtering, sorting, and pagination
- API response and error behavior
- EF Core persistence and migrations through integration tests
- Producer queue publishing, consumer processing, retries, idempotency, and failure handling for email notifications

Prefer unit tests for isolated business behavior and integration tests for database, API, and external-service boundaries. Use test doubles only where they improve isolation; do not replace all integration coverage with mocks.

Before delivery, run formatting, analyzers, unit tests, integration tests, database migration checks, and the production build. Update `README.md` with prerequisites, configuration, database setup, migrations, API execution, Swagger access, email configuration, Docker Compose commands, and test commands.

Do not mark a feature complete until its success path, validation behavior, failure handling, persistence behavior, and relevant automated tests have been verified.
